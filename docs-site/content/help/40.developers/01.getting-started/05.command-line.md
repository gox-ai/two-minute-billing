`tmb` is the Two Minute Billing command line. It sends your test business's events to the webhook
route on your machine, signed, with no tunnel. It also creates test payments, moves the test clock,
pushes a catalog file, compares an invoice with the figures you expect and resets a test business.
It needs Node 20 or later and has no dependencies.

## Install the CLI

Run it once without installing, or add it to your project:

::code-group
```sh [npx]
npx @two-minute-billing/cli doctor
```

```sh [pnpm]
pnpm add -D @two-minute-billing/cli
pnpm exec tmb doctor
```
::

The package is `@two-minute-billing/cli` on the npm registry (MIT). The command it installs is
`tmb`. Run `tmb --help` for the list of commands, and `tmb <command> --help` for the options and
exit codes of one command.

## Give it your settings

`tmb` reads four settings from the environment. It also loads `./.env` when that file exists, or
the file you give with `--env-file <path>`. A variable that is already set in the environment wins
over the file.

| Variable | Value |
|---|---|
| `TMBILLING_URL` | The API host: `https://api.twominutebilling.com` on Cloud, your own API host when you self-host |
| `TMBILLING_API_KEY` | A test key (`sk_test_…`) |
| `TMBILLING_BUSINESS_ID` | The test business (`biz_…`). Each command also takes `--business` |
| `TMBILLING_WEBHOOK_SECRET` | The signing secret your app checks. For `tmb listen` alone, any value that your app and `tmb` both read |

`tmb` never prints the API key or the webhook secret. Every command that changes data refuses a key
that is not a test key, and exits with code `3`. `tmb` asks the server for the key's mode
(`GET /v1/me`). For an older server that does not give the mode, it reads the `sk_test_` prefix.
Find your test key and business id in [Test and live mode](/help/developers/getting-started/test-and-live).

## Check your setup

```sh [terminal]
tmb doctor
```

Shows the server, the organization, the key's mode and access, and the businesses the key can
see. It exits `0` for a test key that is ready, `1` when a setting is missing, `2` when the server
or the key fails, and `3` for a live key that can write. With `--allow-live-read`, a live
read-only key exits `4` instead of failing. Add `--json` for output a script can read.

## Add the Agent Skills

```sh [terminal]
tmb init
```

`init` does three things:

1. It asks, then runs `npx skills add https://twominutebilling.com` to install the Agent Skills.
   With `--yes` it does not ask.
2. It adds the four setting names, with no values, to `.env.example` (or to `.env.sample` or
   `config/.env.example` when one of them exists). It never changes `.env`.
3. It shows the next steps: the values to set in `.env`, `tmb doctor`, and how to connect an AI
   assistant with a read-only key.

[SDKs and tools](/help/developers/getting-started/sdks#set-up-with-a-coding-agent) tells you what
the skills do.

## Forward events to your local route

```sh [terminal]
tmb listen --forward http://localhost:3000/webhooks/billing
```

`listen` gets the test business's new events every two seconds and sends each one to your route.
The body and the `Tmbilling-Signature` and `Tmbilling-Event-Id` headers are the same as a webhook
endpoint gets, so your handler runs its real signature check. `listen` signs with
`TMBILLING_WEBHOOK_SECRET`.

You need no tunnel and no registered endpoint. `listen` gets the events from the API and posts
them from your machine, so your route can stay on `localhost`. For local use, the secret can be any
value that your app and `listen` both read.

`listen` shows one line for each event: the time, the type, the event id, your route's HTTP status
and how long it took. Press Ctrl-C to stop.

| Option | What it does |
|---|---|
| `--forward <url>` | The route to send events to. Required |
| `--events invoice_paid,payment_failed` | Sends only these event types. Without it, `listen` sends every event |
| `--interval 2s` | How often `listen` gets new events: `2s` by default, `250ms` or more |
| `--since now` | `now` (the default) sends only the events that occur after the start. `10m` also sends the events of the last ten minutes, and an ISO time starts from that time |
| `--business biz_…` | The test business, when it is not `TMBILLING_BUSINESS_ID` |
| `--allow-remote` | Allows a `--forward` URL that is not `localhost`, `127.0.0.1` or `[::1]` |

`listen` sends each event once and shows the result. It does not retry a failed send, and the
sends are not in the endpoint's delivery log. To test retries and the delivery log, register an
endpoint at a URL that the engine can reach, as described in
[Delivery and retries](/help/developers/webhooks/delivery).

::tip{title="Use listen with Time Travel"}
When you move the test clock, the renewals, invoices and failed payments that it runs send their
events too. `listen` forwards them to your route, so you can test a year of billing on your
machine.
::

## Test your webhook route

```sh [terminal]
tmb webhooks test --url http://localhost:3000/webhooks/billing
```

Sends three requests to your route: one with a bad signature, which must get `401`, one signed
event, which must get a `2xx`, and the same event again, which must also get a `2xx`. The event
type is `customer_updated` unless you give `--type`. It accepts loopback URLs only. It exits `0`
when all three pass and `2` when one fails.

## Register an endpoint

```sh [terminal]
tmb webhooks register --url https://app.example.com/webhooks/billing
```

Creates a webhook endpoint and appends its signing secret, as `TMBILLING_WEBHOOK_SECRET`, to your
env file: the `--env-file` file, else `.env`, or the file you give with `--env-file-out`. It never
prints the secret. It refuses when the env file is tracked by git or already has a secret. Give
`--events a,b` to send only some event types. Without it, the endpoint gets every event. See
[Webhooks](/help/developers/webhooks) for what the endpoint receives.

## Create test payments

```sh [terminal]
tmb trigger purchase
```

Creates a new test customer with a test card, then a purchase or a subscription, so that real
events occur:

| Scenario | What it does | Events |
|---|---|---|
| `purchase` | The customer buys a one-time price with the card 4242 4242 4242 4242 | `invoice_paid`, `payment_succeeded` |
| `payment-failed` | The same with the card 4000 0000 0000 0002, which declines | `payment_failed` |
| `subscription` | The customer subscribes to a recurring price | `subscription_created` |

Without `--price`, `trigger` uses the first active price of the correct type and shows its id. It
exits `2` when it creates the objects but the outcome is not the expected one. Run it while
`tmb listen` is running to see the events reach your route.

## Move the test clock

```sh [terminal]
tmb clock start
tmb clock advance --by 1m
tmb clock status
tmb clock stop
```

Moves the clock of a test business with Time Travel, so renewals, trial ends and dunning run now.
`start` takes `--at <ISO time>`. `advance` takes `--by` with `h`, `d`, `w`, `m` or `y` (`1m` is one
month, not one minute), or `--to <ISO time>`. `stop` keeps the test data unless you add `--wipe`.
See [Fast-forward the clock](/help/developers/getting-started/test-and-live#fast-forward-the-clock).

## Push your catalog

```sh [terminal]
tmb push billing.catalog.json
tmb push billing.catalog.json --apply
```

Without `--apply`, `push` shows the changes that the catalog file asks for and changes nothing.
With `--apply`, it makes them. It never changes the terms of a price: give new terms a new price
id. It exits `2` on a conflict, and then applies nothing.

## Check an invoice

```sh [terminal]
tmb check --expected expected.json --subscription sub_XXXXXXXXXXXX01
```

Gets the invoice from the API and compares it with the figures in `expected.json`, in minor units.
Select the invoice with `--invoice inv_…`, `--subscription sub_…` (its newest invoice) or
`--session cosess_…` (the invoice a checkout created). `--report out.json` writes the result to a
file. It exits `0` when every field matches and `2` when a field is different.

## Reset a test business

```sh [terminal]
tmb reset
```

Deletes all the data of a test business: the customers and every subscription, invoice, payment
and credit note, the catalog, coupons, taxes, dunning, webhook endpoints, gateways and email
settings. Time Travel stops. The business id, team members, API keys and the audit log stay.

::warning{title="You cannot undo a reset"}
`reset` asks you to type the business id. In a script, give it with `--confirm biz_…`. With no
terminal and no `--confirm`, `reset` stops. It refuses a live business.
::

[Reset a test business](/help/developers/getting-started/test-and-live#reset-a-test-business)
lists what the reset copies again from the live business.

## Read the exit codes

| Code | Meaning |
|---|---|
| `0` | Done |
| `1` | Bad input or a failed request |
| `2` | A check failed, or the outcome is not the expected one |
| `3` | The key is not a test key |
| `4` | `tmb doctor` only: a live read-only key, with `--allow-live-read` |
