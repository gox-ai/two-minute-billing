Some products sell credits, not money. One image costs 1 credit, an edit costs half a credit, a
pack of 15 credits costs USD 9.00 and a pack of 50 costs USD 25.00. One credit has no fixed money
value, so a usage price in money does not fit. This recipe makes a credit unit with no money
value, gives each meter a cost in credits, and lets each usage event take its credits when it
arrives.

For credit that has a money value ("1 credit = USD 0.01"), where usage bills on the invoice and
credit pays the usage line, see [Prepaid AI credits](/help/developers/recipes/prepaid-ai-credits).

## How it works

| | Credit with a money value | Credit with no money value |
|---|---|---|
| The unit | `minor_per_unit: "1"` | `minor_per_unit: null` |
| Usage is priced by | A price on the meter, in money | A credit cost on the meter |
| Credit is spent | When the invoice is finalized | When each usage event arrives |
| Not enough credit | The rest bills on the invoice | The event is refused with 402 |
| Revenue | On the invoice | At each settlement, at what the customer paid for the credits |

1. Create a credit unit with no money value.
2. Give customers credit in it: packs they buy, credits in their plan, credit you give.
3. Set a credit cost on each meter, for example 1 credit for each image.
4. Send usage events as usual. Each event takes its credits from the customer's balance when it
   arrives. When the balance is too small, we refuse the event with 402.
5. Each hour, a settlement draws the credits used from the grants and books the revenue. The
   period invoice states what credits paid, with no amount.

## Create a unit with no money value

Send `minor_per_unit: null`. The field is required: a request without it is refused with 400,
so you never get a unit with no money value by mistake.

```bash [curl]
curl -X POST $TMBILLING_URL/v1/businesses/$BIZ/credit_units \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "id": "credit",
    "name": "credit",
    "plural_name": "credits",
    "currency": "USD",
    "minor_per_unit": null,
    "decimals": 1
  }'
```

```json
{
  "object": "credit_unit",
  "id": "credit",
  "name": "credit",
  "plural_name": "credits",
  "currency": "USD",
  "minor_per_unit": null,
  "rated": false,
  "decimals": 1,
  "locked": false,
  "locked_at": null,
  "status": "active",
  "created_at": "2026-11-13T09:00:00.000Z",
  "updated_at": "2026-11-13T09:00:00.000Z",
  "resource_version": 1
}
```

- `currency` is the currency of the packs that sell the credit, and of the revenue it earns.
- `decimals` is how finely a credit divides. An edit that costs 0.5 credit needs `decimals: 1`.
  Then every `amount` in the unit is in tenths: 15 credits is `"amount": 150`.
- The first grant in the unit locks `currency`, `minor_per_unit` and `decimals` (`locked: true`).
  After that, only the names can change.

In the dashboard: **Settings → Credit units → Create credit unit**, and under **Money value**
select **No money value**.

## Give credit in the unit

Each lot of credit is a **credit grant**. A grant in this unit has `face_minor: 0`: its only money
is its **cost basis**, what the customer paid for it. "15 credits, bought for USD 9.00" is a grant
with `amount: 150` and `cost_basis_minor: 900`.

### Sell packs

A pack is a one-time price with `grants_credit`:

```bash [curl]
curl -X POST $TMBILLING_URL/v1/businesses/$BIZ/prices \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "product": "credit-packs",
    "name": "15 credits",
    "type": "one_time",
    "model": "flat",
    "currency": "USD",
    "amount_minor": 900,
    "grants_credit": {
      "kind": "pack",
      "unit": "credit",
      "amount": 150,
      "category": "paid",
      "expires_after": { "days": 30 },
      "tax_treatment": "taxed_at_purchase"
    }
  }'
```

When the pack's invoice is paid, the customer gets a paid grant:

```json
{
  "object": "credit_grant",
  "id": "cgr_XXXXXXXXXXXX01",
  "customer": "cus_XXXXXXXXXXXX01",
  "currency": "USD",
  "unit": "credit",
  "amount": 150,
  "amount_decimal": "15",
  "face_minor": 0,
  "cost_basis_minor": 900,
  "category": "paid",
  "source": "purchase",
  "tax_treatment": "taxed_at_purchase",
  "status": "active",
  "remaining": { "units": 150, "units_decimal": "15", "face_minor": 0, "cost_minor": 900 }
}
```

Each credit of this pack earns USD 0.60 when it is used: the cost basis divided by the credits. A
pack of 50 credits for USD 25.00 earns USD 0.50 for each credit. Two customers can pay different
prices for the same credit, and the revenue follows what each one paid.

Credit in a unit with no money value is always taxed at purchase: `taxed_at_use` is refused.

### Include credits in a plan

On a recurring price, `grants_credit` with `kind: "per_cycle"` gives credit each billing period:

```json
"grants_credit": { "kind": "per_cycle", "unit": "credit", "amount": 750 }
```

That is 75 credits each period. Plan credits are promotional: they are part of the plan fee, so
their cost basis is 0. `rollover` and `reset` work as for any unit: see
[Include credits in a plan](/help/developers/recipes/prepaid-ai-credits#include-credits-in-a-plan).

### Give credit by hand

```bash [curl]
curl -X POST $TMBILLING_URL/v1/businesses/$BIZ/customers/$CUS/credit_grants \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{ "category": "promotional", "unit": "credit", "amount": 50, "expires_at": "2027-01-01T00:00:00Z" }'
```

For paid credit, send `category: "paid"`, the net `price_minor` (the cost basis) and
`tax_treatment: "taxed_at_purchase"`. We create the invoice, as for any paid grant.

### What we book

| Credit | At the sale | When it is used | At expiry |
|---|---|---|---|
| Paid (packs, paid grants) | The pack price waits as deferred revenue | Its cost basis moves to revenue | What is left is breakage |
| Given (plan credits, promotional) | Nothing | Nothing | Nothing |

Given credit in this unit has no money value and no cost, so it books nothing in the ledger.

## Set the credit cost of a meter

A credit cost says what one unit of the meter costs in credits. Set it with the API:

```bash [curl]
curl -X PUT $TMBILLING_URL/v1/businesses/$BIZ/meters/illustrations/credit_cost \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{ "unit": "credit", "credits_per_unit": "1" }'
```

```json
{
  "object": "meter_credit_cost",
  "meter": "illustrations",
  "unit": "credit",
  "credits_per_unit": "1",
  "overrides": []
}
```

An edit costs half a credit. On the Pro plan it costs 0.4, and one customer's subscription has a
deal at 0.25:

```bash [curl]
curl -X PUT $TMBILLING_URL/v1/businesses/$BIZ/meters/edits/credit_cost \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "unit": "credit",
    "credits_per_unit": "0.5",
    "overrides": [
      { "product": "pro-plan", "credits_per_unit": "0.4" },
      { "subscription": "sub_XXXXXXXXXXXX01", "credits_per_unit": "0.25" }
    ]
  }'
```

The most specific cost wins: the subscription's, then the plan's, then the meter's. A customer
with no subscription pays the meter's own cost.

- An event costs its quantity × `credits_per_unit`, rounded half up to the unit's smallest step,
  for each event. With `decimals: 1`, an edit at 0.25 costs 0.3 credit.
- `credits_per_unit` is more than 0, with at most 6 decimal places.
- The PUT replaces the whole cost: an override that you do not send is removed.
- The unit must have no money value (400 otherwise). After an event spends credits on the meter,
  the meter keeps its unit.
- The meter must count events (`count`) or add a value that only grows (`sum`, not recurring).
  Other meters are refused with 400.
- The PUT refuses a meter that a usage price bills on a live subscription (409): archive that
  price first. A price with a rate can be added to a meter with a credit cost: it bills only the
  usage that credits do not pay. A price that bills event amounts is refused (400).
- `GET …/meters/{meter}` shows the cost as `credit_cost`, or `null`.
- `DELETE …/meters/{meter}/credit_cost` stops it. Events that arrive after that spend no
  credits. Credits already taken stay taken.

The key needs `meters:manage`.

## Send usage events

Send events as in [Meter usage events](/help/developers/recipes/meter-usage-events). Nothing
changes in the request:

```bash [curl]
curl -X POST $TMBILLING_URL/v1/businesses/$BIZ/usage_events \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "key": "image-XXXXXXXXXXXX01", "customer": "workspace-4821", "event_name": "illustration" }'
```

The credits leave the balance in the same transaction that stores the event. The answer is 201,
and the event has a `credit` entry for each meter with a credit cost:

```json
{
  "status": "created",
  "event": {
    "object": "usage_event",
    "key": "image-XXXXXXXXXXXX01",
    "customer": "cus_XXXXXXXXXXXX01",
    "customer_key": "workspace-4821",
    "event_name": "illustration",
    "status": "matched",
    "meters": ["illustrations"],
    "credit": [
      {
        "meter": "illustrations",
        "unit": "credit",
        "status": "taken",
        "reason": null,
        "quantity": "1",
        "credits_per_unit": "1",
        "cost_source": "meter",
        "credits_due": "1",
        "credits_taken": "1",
        "credits_from_closed_grant": "0",
        "credits_uncovered": "0",
        "covered_by_hold": false
      }
    ]
  }
}
```

`status` moves from `taken` (left the balance, waiting for settlement) to `settled`. `pending`
means a grant that ended pays it, in its grace window (see [Late events](#late-events)). Many
events at the same time never take the balance below zero: 40 events sent together against 5
credits give 5 accepted and 35 refused.

### When the credit is used up

When the customer does not have enough credit, the answer is 402:

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "insufficient_credit",
    "message": "We could not take credits for the event. The customer does not have sufficient credit. The event is stored and is not billed."
  }
}
```

- The event is **stored**, with `credit[].status: "refused"` and `reason: "insufficient_credit"`.
  It spends nothing, and it is never billed.
- A `credit_usage_refused` webhook is sent. Its `data.credit_usage` has the event's key, the
  customer, the meter, `credits_due`, `credits_available` and the `policy` that applied.
- A repeat of the same key answers 402 again. It does not take credits on a second try: send a
  new event with a new key after the customer buys credit.
- In a batch, the refused event has `status: "error"` with `code: "insufficient_credit"`, and the
  other events go on.
- An event that two meters count is accepted or refused whole: it never pays one meter and not
  the other.

What happens to usage past the credits depends on the `on_exhausted` policy and the prices:

- `block` refuses the event, as above.
- `bill` accepts the event when there is an overage price: the rate price of the meter on a live
  subscription of the customer, or the unit's `overage_minor_per_unit` (the meter's price comes
  first). The next period invoice bills
  the credits that were missing, in money. With no overage price, `bill` refuses as `block` does.
- An overdraft limit (`overdraft_limit` on the unit, a plan or a customer) lets the balance go
  below 0, up to the limit, before anything is refused or billed. Credits that the customer buys
  pay a negative balance first. A plan renewal carries it or forgives it
  (`negative_balance_at_reset`). To set one existing customer's policy, send
  `PATCH …/customers/{cus}` with `credit_settings: { on_exhausted, override_expires_at?, overdraft_limit_minor? }`
  (replaced whole), and `PUT …/customers/{cus}/credit_overdraft_limits/{unit}` with
  `{ "overdraft_limit": <smallest steps> }` for one unit.
- A customer with no live subscription blocks at 0 by default (policy source `no_subscription`).
  `credit_config.no_subscription_usage: as_subscriber` gives them the same `block` or `bill` rules
  as a subscriber. Their overdraft needs a unit overage price, and by default also a saved payment
  method and no unpaid overage invoice (`no_subscription_overdraft`: `needs_payment_method`,
  `always` or `never`). A one-off invoice bills what they owe once the oldest part is
  `no_subscription_invoice_after_days` old (default 30).
- During a free trial, usage past the credits is refused by default: no overage, no overdraft.
  The policy source is `trial`. `credit_config.trial_usage: overdraft_only` allows the overdraft
  limit; `as_paid` applies the rules of a paid subscription, and the first invoice after the trial
  bills the overage. In a trial the balance goes below 0 only when the unit has an overage price,
  so a trial that ends with no paid subscription is invoiced like a customer with none. A unit's
  automatic top-up waits for the trial to end.

The webhook's `policy` names the one that applied. A refused event counts in your cost and
margin reports, but not in usage totals or allowances.

One exception: an event that captures a credit hold
(`POST …/credit_holds/{hold}/capture` with a `usage_event`) is never refused. It takes the
credits that are left and records the rest in `credits_uncovered`. With
`credit_config.capture_over_hold: cap_at_hold`, it takes no more than the hold: the rest is not
charged and shows in `credits_past_hold`.

In your app, treat a 402 as "not paid":

```ts
import { Tmbilling, TmbillingError } from "@two-minute-billing/sdk";

const tmb = new Tmbilling({ apiKey: process.env.TMBILLING_API_KEY! });

/** True when the customer's credits paid for the image. */
export async function chargeImage(biz: string, workspaceId: string, imageId: string) {
  try {
    await tmb.usageEvents.send(biz, {
      key: `image-${imageId}`,
      customer: workspaceId,
      event_name: "illustration",
    });
    return true;
  } catch (e) {
    if (e instanceof TmbillingError && e.status === 402) return false; // ask them to buy credits
    throw e; // keep the event and retry it with the same key
  }
}
```

### Which grant pays

A grant pays only while its life contains the moment the event arrives. A grant that starts
later does not pay yet. A grant that has ended does not pay a new event, even before the expiry
job runs. It pays only a late event, as below.

A plan's credit for a billing period keeps paying after the period end until the renewal runs,
for at most the business's usage close wait plus one hour. The renewal then closes it and gives
the next period's credit.

### Late events

An event can arrive after the moment it records. `credit_config.late_event_grace_hours` on the
business sets how late (default 12, from 0 to 840; 0 turns it off):

- An event that arrives within the grace hours of its `timestamp` is paid first by the grant that
  was live at that timestamp, even if that grant has ended since.
- Any other event is paid by the balance when it arrives.
- An event more than 35 days old is refused with 422 `timestamp_too_old`, as for every meter.

For example, a pack expires at 12:00 with 9 credits left. At 13:00 your app sends an image dated
11:00: the pack pays it. An event sent at 13:00 and dated 13:00 cannot use the pack. At 00:00, when
the 12 hours end, what is left of the pack lapses: for a paid pack, it is breakage.

To import usage that is already paid for, for example when you move from another system, send
`"backfill": true`. The event is recorded and counted on its meters, and it spends no credits
(`credit[].status: "skipped"`, `reason: "backfill"`).

### Void an event

`POST …/usage_events/void` gives the credits back while no settlement has drawn them. After the
settlement, the void is refused with 409. Settlement runs each hour, so void a wrong event soon.

## Settlement

A settlement draws the credits that events took from the customer's grants, and books the
revenue. It runs:

- each hour, for the events that arrived before the top of the hour;
- in the period invoice, for all the usage that is not settled yet, before the invoice is
  written;
- before a grant expires or is voided, before a rollover and before a credit note on a pack.

Grants pay in the same order as on an invoice: restored credit, the lowest `priority`, the
soonest expiry, promotional before paid, then the oldest. A grant pays only usage that arrived
inside its life.

For paid credit, each settlement books the cost basis of the credits drawn as revenue. Four
images drawn from the pack of 15 credits for USD 9.00 earn USD 2.40:

```bash [curl]
curl "$TMBILLING_URL/v1/businesses/$BIZ/customers/$CUS/credit_usage?meter=illustrations" \
  -H "Authorization: Bearer $TMBILLING_API_KEY"
```

```json
{
  "object": "list",
  "data": [
    {
      "object": "credit_usage",
      "id": "cst_XXXXXXXXXXXX01",
      "customer": "cus_XXXXXXXXXXXX01",
      "meter": "illustrations",
      "unit": "credit",
      "kind": "usage",
      "status": "settled",
      "window_start": "2026-11-13T09:10:00.000Z",
      "window_end": "2026-11-13T10:00:00.000Z",
      "events": 4,
      "quantity": "4",
      "credits_due": "4",
      "credits_drawn": "4",
      "quantity_uncovered": "0",
      "currency": "USD",
      "revenue_minor": 240,
      "created_at": "2026-11-13T10:00:04.000Z"
    }
  ],
  "has_more": false,
  "next_cursor": null
}
```

`kind: "late"` is a settlement of late events that an ended grant paid in its grace window. In
`GET …/credit_transactions`, each draw names its settlement in `settlement`. The
`credit_usage_settled` webhook goes only to an endpoint that lists it by name.

## On the invoice

The period invoice of the customer's oldest subscription states what credits paid, one line for
each meter:

> Illustrations: 120. Paid with 120 credits.

The invoice prints these lines under **Usage paid with credits**, with no amount and no tax. They
cover the usage that arrived since the last such line, up to the period end. They add nothing to
the total, and a credit note does not list them.

## Limit free credit

A money limit on free credit cannot apply to a unit with no money value. Each unit has its own
limit, in its smallest step, in `credit_config.unit_grant_limits`:

```bash [curl]
curl -X PATCH $TMBILLING_URL/v1/businesses/$BIZ \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{ "credit_config": { "unit_grant_limits": { "credit": { "max_units": 10000, "alert_above_units": 5000 } } } }'
```

With `decimals: 1`, that is a maximum of 1,000 credits and an alert above 500 credits, for each
promotional grant that you give by hand:

- Above `max_units`, the grant is refused with 400: "We could not give the credit grant. The
  maximum for one grant is 1000 credits. Enter a smaller amount, or change the maximum in
  Settings > Credits."
- Above `alert_above_units`, the grant is given, written to the audit log, and sent to your team
  if the large grant alert is on.

The PATCH replaces the whole `credit_config`, so send every key you want to keep.
`unit_grant_limits` and `late_event_grace_hours` are kept when you leave them out. Send
`"unit_grant_limits": {}` to remove every unit limit. In the dashboard: **Settings → Credits →
Limits on free credit with no money value**, in whole credits.

## Take credit back

- **A promotional grant:** `POST …/credit_grants/{grant}/void`. What is left leaves the balance.
- **A pack:** a credit note on the pack's invoice line, for the unused part only, in proportion
  to the cost basis. A customer who used 6 of 15 credits from a USD 9.00 pack can get at most
  USD 5.40 back, and the note voids the 9 credits that are left. Usage that is not settled yet is
  settled first.

## See your margin

Send your cost on each event, as in [See your margin](/help/developers/recipes/bill-ai-tokens#see-your-margin):
add up what the provider calls behind one action cost, and send the total as `cost` (major units,
with `currency`). Then:

- `GET …/customers/{cus}/credit_usage` gives `revenue_minor` for each settlement: what the credits
  used earned, at the price the customer paid.
- `GET …/reports/usage_margin?scope=all` shows the cost of a meter with a credit cost as cost
  only, because no invoice line bills it. By customer, `total_revenue_minor` includes the pack
  sales. The cost-only figures are written each night, for the days up to yesterday.
- The default `scope=billed` reads invoice usage lines only, so it does not show these meters.

The cost of every event that is not voided counts, a refused event too.

## In the TypeScript SDK

Every write takes `opts?: { idempotencyKey }`.

| Call | Does |
|---|---|
| `tmb.creditUnits.create(biz, body)` | Creates a unit. `minor_per_unit` is required: a rate, or `null`. |
| `tmb.creditUnits.list(biz, { limit, startingAfter, status })` | Lists the units. |
| `tmb.creditUnits.get(biz, unit)` · `.update(biz, unit, body)` · `.archive(biz, unit)` | Reads, changes or archives a unit. |
| `tmb.meters.getCreditCost(biz, meter)` | Reads a meter's credit cost. |
| `tmb.meters.setCreditCost(biz, meter, body)` | Sets the cost and its overrides (`PUT`). |
| `tmb.meters.deleteCreditCost(biz, meter)` | Stops the credit cost. |
| `tmb.creditUsage.list(biz, cus, { limit, startingAfter, meter })` | Lists what events took and each settlement. |

`tmb.usageEvents.send` takes `backfill: true` for usage that is already paid for, and a sent
event has `credit`: what each grant gave. Types: `CreditUnit`, `CreditUnitCreate`,
`MeterCreditCost`, `MeterCreditCostSet`, `MeterCreditCostOverride`, `CreditUsage`,
`UsageEventCredit`.
