**Goal:** take a copy of a business's billing data: for your accounts, your data warehouse, or to
move it into another business. An export is one zip of CSV files, all taken at the same moment,
and every file has the columns that [Import from CSV files](/help/developers/recipes/import-from-csv-files)
reads. A file you export imports into another business as it is.

An export has three steps: preview, start, and download. It runs in the background.

## Preview

Send the record types you want and, for each one, the rows to keep. The preview writes nothing.
It counts the records of each file and returns the first rows exactly as the file will have them.

```bash
curl -X POST $TMBILLING_URL/v1/businesses/$BIZ/exports/preview \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "entities": ["invoices", "payments"],
    "filters": {
      "invoices": { "status": ["paid", "open"], "from": "2026-01-01" },
      "payments": { "from": "2026-01-01" }
    }
  }'
```

| Record type | File | Filters |
|---|---|---|
| `plans`, `addons` | one row for each price | `include_archived` |
| `coupons` | one row for each coupon | `include_archived` |
| `customers` | one row for each customer, with the saved card reference | `from`, `to`, `date_field` (`created` or `updated`) |
| `subscriptions` | one row for each item of a subscription | `status` (`active`, `trialing`, `future`, `paused`, `non_renewing`, `cancelled`), `from`, `to`, `date_field` |
| `invoices` | one row for each line of an invoice | `status` (`paid`, `open`, `void`), `from`, `to` (the invoice date) |
| `credit_notes` | one row for each credit note | `from`, `to` |
| `payments` | one row for each payment or refund | `status` (`succeeded`, `failed`), `from`, `to` |
| `usage` | one row for each usage record | `from` (required), `to` |

`from` is inclusive and `to` is not. Each takes a date (`2026-01-01`) or an ISO 8601 instant.

**Records they refer to come too.** By default (`include_related: true`) an export also writes the
records that the chosen rows need: an invoice's customer, subscription and prices; a
subscription's customer, prices and coupons; the payment that a refund returned. So an export of
last month's invoices still imports on its own. The preview gives, for each file, `chosen` (rows
your filters chose) and `related` (rows added because other rows refer to them). Send
`include_related: false` to write only what the filters choose.

## Start

```bash
curl -X POST $TMBILLING_URL/v1/businesses/$BIZ/exports \
  -H "Authorization: Bearer $TMBILLING_API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{ "entities": ["plans", "addons", "coupons", "customers", "subscriptions"] }'
```

The answer is the export with `status: "queued"`. Read it with
`GET /v1/businesses/$BIZ/exports/$ID`: `progress` shows the file being written while it runs, and
`status` becomes `succeeded` or `failed`. You can also listen for the `export_completed` and
`export_failed` webhooks. The member who started an export in the dashboard gets an email when it
ends.

One export runs at a time in a business. A second start while one runs is a `409`.

## Download

```bash
curl $TMBILLING_URL/v1/businesses/$BIZ/exports/$ID/file \
  -H "Authorization: Bearer $TMBILLING_API_KEY" -o export.zip
```

The zip has one CSV for each record type that had rows, and a `README.txt` that says when the
export was taken, how many rows each file has, and what was left out. To get one file, use
`GET /v1/businesses/$BIZ/exports/$ID/files/customers`.

Each download is in the audit log. The files are kept for 7 days (`expires_at`), then deleted;
the export stays in the list with its counts. To delete the files sooner, use
`POST /v1/businesses/$BIZ/exports/$ID/delete`.

## The files

- **The import's columns first.** Each file starts with the columns of the import template for
  its record type, in the same order and format: amounts in the currency's main unit (`49.00`),
  dates and times in ISO 8601 UTC, lists separated by `|`. Columns that the import does not read
  come after them, such as `mrr` on subscriptions and `amount_paid` on invoices.
- **One moment.** Every file is read from the same snapshot, so an invoice and its payments agree.
- **Invoices.** The tax and the discount are on the first line of each invoice, and the lines,
  less the discount, plus the tax, make the total, as the import checks.
- **Text that a spreadsheet could run.** A value that starts with `=`, `+`, `-` or `@` gets a `'`
  before it, so a spreadsheet shows it as text. The import removes that `'`.
- **Left out.** Drafts, usage prices (create them in the other business before you import usage)
  and pricing models the import cannot read are not in the files. `skipped` on the export and the
  README count them, with the reason.
- **Card numbers are never in a file.** A customer's card is a reference to the card saved at
  your payment gateway.

## Permissions

Exporting needs `exports:manage` (start, delete) and `exports:view` (preview, read, download).
Owners and admins have both. A custom role can have them without the import permissions.
